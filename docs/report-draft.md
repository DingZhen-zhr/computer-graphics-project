# 实验报告（初稿）：Datum 基准——基于 SimpleCADAPI 的 CAD 建模智能体

> 初稿。"测试与结果"一节的数字等计划 4 的真实评测跑完后从 `docs/results-v3.md` 抄过来；现在还没有测的地方都照实写了"还没有测"。

## 1 系统设计

Datum 是一个桌面应用：用户用一句话说想做什么，它和用户把需求问清楚，然后用 SimpleCADAPI（SCA）一步一步把零件或产品建出来，每一步都由程序实测，最后交付参数化源文件、STEP 和截图。核心思路是**程序管流程和关卡，模型只做判断和写代码**。

```
 用户一句话
     │
     ▼
 ┌────────────┐  缺什么问什么      ┌────────────┐
 │  澄清需求   │ ───────────────▶ │  需求单     │  参数标明"你给的 / 建议"
 └────────────┘                   └─────┬──────┘
                                        │ 用户确认
                                        ▼
 ┌──────────────────────────────────────────────────────┐
 │  分阶段建模（每个零件）                                  │
 │  计划 → 每一步：先写检查 → 写特征 → 沙盒里运行并实测      │
 │        没过：把量到的差距和出错位置交回模型，改好再跑     │
 │  零件终检：每个尺寸改一改，检查要能发现（参数扰动）        │
 └──────────────────────────┬───────────────────────────┘
                            │ 多个零件时
                            ▼
 ┌──────────────────────────────────────────────────────┐
 │  装配与运动：连接点挂在真实几何上 → 配合 → 关节           │
 │  装好时不穿模；每个关节从头到尾取样，每个位置检查碰撞      │
 │  产品终检：改一个参数，重做用到它的零件和装配             │
 └──────────────────────────┬───────────────────────────┘
                            ▼
                交付：源文件、STEP、STL、截图、运动数据
```

**程序管关卡。** 模型只能通过工具改需求单、计划、特征、检查和装配声明；什么时候能建模（需求单确认后）、什么时候算这一步通过（检查全过）、什么时候能交付（终检通过）都由程序判断。工具的返回里带着下一步该做什么的提示，出错时把 SCA 的报错翻译成"哪个特征、什么原因、怎么改"。

**分阶段。** 模型先把零件拆成 1–12 步（外形、开孔、加筋、边角处理……），每一步先写这一步的检查，再写特征，然后运行。通过的步骤在上下文里折叠成一段小结，让上下文保持短，也让服务端的前缀缓存能用上。

**检查和终检。** 检查是声明式的：包围盒、选中几何的个数、两个面的距离和夹角、某个点在不在材料里、体积。选几何用 SCA 的查询语言（面的类型、法向、中心、面积）。终检把用户给的每个参数改大改小 20%，重建以后检查必须有一条不通过——这样能发现"模型其实没用上这个参数"或"没有检查管住它"的情况。只出现在关节范围里的参数（如"盖子最多翻多少度"）由运动取样直接覆盖，不做扰动。

**沙盒。** 模型写的代码先过静态检查（不能 import、不能访问文件），再在独立的子进程里运行，带超时、可以中途停下，环境变量里的 key 被去掉。

**多零件与运动。** 每个零件在自己的坐标里建模；装配用"连接点 + 配合 + 关节 + 联动"声明：连接点必须恰好选中零件上一个真实的圆柱面、平面或圆形的边，程序取它的轴线或法向；配合把两个连接点对上（同向或反向、间隙、转角），关节声明转动或滑动和范围，联动表示齿轮、皮带的传动比。摆放和姿态由程序计算（纯 Python，可以单元测试），重叠体积用 OCP 的布尔运算量。界面播放的运动和碰撞检查用的是同一份取样。

**界面。** "展台"风格：零件是画面主角，浅色影棚、深色黑曜；需求单在澄清时就在舞台中间边聊边填；对话记录、检查、版本收在抽屉里；能转到任意角度看、有坐标轴小图、剖开、正交；多零件能单独看、炸开、透视、播放运动；调参数直接改数值、不花钱；能对比修改前后的两个版本。

## 2 测试与结果

评测有 14 个任务：开发 10 个（用来分析和改进），留出 4 个（只用来测，不看对话记录）。其中 3 个是多零件、会动的任务（带铰链盖的工具盒、带抽屉的小柜子、一对啮合的齿轮）。每个任务由一个"模拟用户"（另一个大模型，手里拿着完整的隐藏需求，只回答被问到的）和智能体对话，从一句话需求走到交付，再提一次修改；每次交付后用任务文件里人工手算的验收条目，对交付的模型独立重新测量（多零件任务的验收不读内核写的运动数据，自己把关节放到位再量）。

每个评测任务都有一份写好的标准答案，在真实的 SCA 里验证过：初始和修改后的验收都能全过，没按修改改的旧版本恰好卡在修改相关的条目上。这保证了验收本身是对的。

**真实模型的结果：还没有测。** 计划 4 会用 `deepseek-flash` 跑两轮，花费上限 ¥20（按实际扣费，包括模拟用户的调用）。跑完后在这里填：开发和留出各成功几个、最大尺寸偏差、平均耗时、修复次数、覆盖情况（需求澄清、多轮修改、错误反馈修正），以及失败分析的结论。

## 5 不足与后续

- 真实模型的效果还没有测（见第 2 节）；多零件的提示词和工具说明能不能让模型真的做出工具盒、抽屉柜、齿轮对，要等评测。
- 多零件只支持树形的装配（每个零件被一个配合装上去），不支持闭环机构（比如曲柄滑块）。
- 多零件交付时不做看图审查；单零件的看图审查需要能识图的模型。
- 界面只在 Windows 上看过，Mac 上没有看过；真的桌面窗口里也没有完整走过一遍（在应用内置浏览器里走过）。
- 没有用图片作为需求输入，没有英文界面，没有打包成安装包。
