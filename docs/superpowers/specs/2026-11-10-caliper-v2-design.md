# 卡尺 Caliper · 第二版设计

日期：2026-11-10　状态：待审阅
来源：AICG Project 3 作业要求（github.com/syby119/AICG-projects/tree/main/projects/project3）；2026-11-10 与用户逐项议定的结论。
前置文档：第一版设计、第 1.1 版设计（同目录）。本文没有提到的地方，仍以它们为准。

## 1. 目标与范围

**一句话：** 把现在的"网页演示"做成一个产品——别人在终端粘一行命令就能装到自己电脑上，打开是一个桌面窗口，填自己的 API key 就能用自然语言做 CAD 零件，而且做出来的东西经得起检查。

产品名：**卡尺 Caliper**，命令 `caliper`。名字的意思就是这个 harness 的立场：每一步都由程序实测，模型说了不算。

### 1.1 已经议定的事

| 事项 | 结论 |
|---|---|
| 产品形态 | 桌面应用（独立窗口），不是浏览器标签页 |
| 平台 | Windows 10/11 x64；Apple 芯片 Mac、macOS 14 及以上。不支持 Intel Mac（SCA 没有对应安装包）和 Linux |
| 实现与分发 | pywebview 原生窗口 + 一行安装命令（脚本用 uv 准备 Python 环境，从 GitHub 安装） |
| Mac 验证 | GitHub Actions 的 Mac 机器自动跑测试和安装脚本，再由有 M 芯片 Mac 的组员照清单人工点一遍界面 |
| API key | 在界面里填，存系统钥匙串；环境变量仍然有效且优先 |
| 模型服务 | DeepSeek 为默认并重点调优；GLM、Kimi、通义等 OpenAI 兼容服务做预设；另支持 OpenAI 和 Claude 官方接口 |
| 复杂度 | 只做单个零件，架构上不设复杂度上限；装配体留到下一版，数据结构留口 |
| 内核路线 | 吸收 SCA 官方 skill 的方法，但仍由程序管流程、模型只调用我们定义的工具 |
| 看图审查 | 做；当前模型不能识图时自动跳过并写明 |
| 经验复用 | 做：自带案例 + 用户可保存 |
| 界面可选项 | 参数面板直接改数、深色模式、不用 key 的示例会话。不做中英双语 |
| 美术方向 | 图纸 / 蓝图：浅色是米白图纸加墨线，深色是深蓝蓝图加白线 |
| 旧功能 | GitHub Pages 演示站改成产品主页；公网隧道实时体验整套删除 |
| 付费评测 | 本轮默认不跑。评测脚本加花费硬上限，另备一份 ¥15 以内的套餐，由用户决定何时运行 |

### 1.2 这一版不做

装配体、图片或手绘草图作为需求输入、英文界面、打包成 .exe / .dmg 安装包、向量检索、Linux。

### 1.3 成功标准（都不需要花钱）

1. 全部测试在 Windows 和 Mac（GitHub Actions）上通过；第一版到 1.2 版的测试除第 9.3 节列出的以外不删、不放松。
2. 新增的 6 个评测任务（中等 3 个、困难 3 个）各有一份分阶段的标准答案，用真实 SCA 建得出来，并通过人工写的验收。
3. 两个历史失败能被新关卡拦住，有测试为证：改了参数但几何没变（1.1 版留出任务 `enclosure`）；用户参数没有被任何检查真正约束。
4. 一台干净的 Windows 机器和 GitHub Actions 的 Mac 机器上，一行安装命令能装好，`caliper doctor` 全部通过。
5. 用假模型剧本加真实 SCA 沙盒，在桌面窗口里完整走通：引导 → 提需求 → 确认 → 规划 → 逐阶段建模 → 终检 → 交付 → 参数面板改数 → 版本对比 → 存为案例。Windows 由实现者走，Mac 由组员照清单走。
6. key 不出现在任何文件、日志、测试、提交里。

**没有付费运行之前，不能对外宣称第二版的成功率。** 上面六条证明的是"关卡按设计工作、流程表达得了这些零件"，不是"真模型做得好"。README 和报告里要照这个说法写。

## 2. 参考了什么，自己写了什么

老师的要求：可以参考 SCA 文档、Agent Skills 和开源框架，但工具封装、流程控制、结果检查必须自己写。

**参考的：**
- SCA 安装包自带的官方 Agent Skill（`simplecadapi/skill/resources/docs/skill/`，Apache-2.0）。它把单零件建模分成五个角色：需求确认、总体规划、验证规划、细节建模、导出；要求每个阶段先定验证再建模、用故意做错的例子证明检查有效、用小段试验代码验证操作、渲染图交给没参与建模的审查者。它带 11 篇建模纪律文档和草图、标准件的用法说明。
- Claude Code 和 Claude 桌面端的交互方式：会话侧栏、工具调用折叠显示、逐字输出、可以中途停止。

**自己写的（全部）：** 工具定义和实现、流程和关卡、检查格式和测量引擎、参数扰动验证、沙盒、上下文管理、案例库、桌面端界面、安装脚本。官方 skill 的文档只在运行时从用户本机的 SCA 安装包里按需读取，不复制进仓库。

**和官方 skill 的区别：** 官方 skill 是给通用编程智能体看的说明书，靠模型自觉照做；卡尺把同样的方法做成程序强制的关卡，模型跳不过去。这一点写进报告的"原创工作"。

## 3. 内核

### 3.1 新流程

```
澄清 ──确认──▶ 规划 ──▶ 阶段 S1 ──▶ S2 ──▶ … ──▶ Sn ──▶ 终检 ──▶ 交付
 ▲                       每个阶段：先写检查 → 建模 → 程序实测        │
 └──────────────────────── 用户提出修改 ◀───────────────────────────┘
```

程序判定的关卡（模型绕不过）：

| 关卡 | 条件 | 不满足时 |
|---|---|---|
| 进入规划 | 需求单已确认、没有待问问题、位置关系填全（见 3.2） | 建模类工具不可用 |
| 开始建模 | 已有计划 | `upsert_feature`、`set_checks`、`build` 返回"先调用 set_plan" |
| 阶段内写特征 | 本阶段至少已有一条检查 | `upsert_feature` 返回"先为本阶段写检查" |
| 进入下一阶段 | 本阶段的实体有效、检查全过 | 停在本阶段，计一次失败 |
| 进入终检 | 最后一个阶段通过 | — |
| 交付 | 终检三项全部通过（见 3.6） | 退回，计一次失败 |

上限：每个阶段 build 没通过最多 3 次（阶段通过后清零），沿用配置项 `max_build_failures`；每个阶段工具调用最多 25 次，新配置项 `max_tool_calls_per_stage`；规划和终检各按一个阶段算。到上限就停下，把最后一次失败原因告诉用户。分阶段流程每轮的总上限是新配置项 `max_tool_calls_total`，默认 200；原来的 `max_tool_calls`（默认 40）只在关掉分阶段时使用。

### 3.2 需求单：加"位置关系"

需求单新增一栏 `relations`，每项一句话，说明两个部分怎么相接。例："立板的下端和底板的一端重叠，外侧面和底板端面平齐，不是叠在底板上面"。

规则：
- `features` 有两项或更多时，除第一项外，每一项的名字都要在至少一条 `relations` 里出现，否则不能请用户确认。
- `relations` 展示在确认卡片上，由用户确认。
- 确认之后再改 `relations`，确认状态清零。

这条针对 1.1 版没解决的"L 形支架叠放"。它不保证模型问得对，但保证相接方式被写下来、被用户看见。

### 3.3 计划与阶段

**计划** 是一个阶段列表，每个阶段有 `id`（`s1`、`s2`…）、`title`（做什么）、`done_when`（这个阶段做完后零件上多了什么）。1 到 12 个阶段。简单零件可以只有一个阶段。

**特征和检查都归属某个阶段。**
- `upsert_feature` 新增的特征归当前阶段；修改已有特征时归属不变。
- 检查带两个新字段：`stage`（从哪个阶段开始成立）和 `holds`。`holds` 取 `from_here`（默认，从这个阶段起一直成立）或 `here_only`（只在这个阶段结束时成立，例如"打孔之前底板的体积"）。

**build 的含义变成"从当前阶段尽量往后推进"：**
1. 把截到当前阶段的特征拼成 notebook 运行。
2. 跑必做检查，加上所有 `stage` 不晚于当前阶段的 `from_here` 检查，加上当前阶段自己的 `here_only` 检查。
3. 全过：阶段通过，导出该阶段的 STL（给界面的阶段回看用），当前阶段后移。如果下一个阶段已经有特征和检查（修改后重新验证时会这样），程序不回到模型，接着验证下一个阶段。
4. 没过：停在这个阶段，返回哪个特征、哪条检查、实测数值。

**怎么取到各阶段末尾的实体：** 每个阶段各跑一次截断的 notebook，最多 4 个进程并行，不花钱。"一次运行取到每个阶段末尾的实体"是否可行，实施时探测一下并记进 `docs/sca-api-notes.md`，留作以后的优化，这一版不做。

**改计划：**
- 还没通过的阶段可以用 `set_plan` 重排。
- 已通过的阶段，其特征被修改或删除时，从那个阶段起全部标成未通过，当前阶段退回到那里。
- 交付之后用户要加新特征：模型用 `set_plan` 在末尾追加阶段。
- 交付之后只改参数数值：程序自动从 S1 起重新验证全部阶段再过终检，不需要模型动手（沿用 1.1 版的自动重建）。

### 3.4 工具

保留现有 9 个：`update_brief`、`ask_user`、`request_confirmation`、`upsert_feature`、`remove_feature`、`set_checks`、`build`、`inspect`、`api_help`。

改动：
- `update_brief` 的 patch 多一个键 `relations`。
- `set_checks` 多一个必填参数 `stage`，只替换这个阶段的检查；每条检查可带 `holds`。
- `build` 的返回多出阶段信息：通过了哪些阶段、现在停在哪个阶段、是否进入终检、终检结果。

新增 3 个：

| 工具 | 作用 | 限制 |
|---|---|---|
| `set_plan(stages)` | 提交或修改分阶段计划 | 需求单已确认后可用；已通过的阶段不能改 |
| `probe(code)` | 在沙盒里跑一小段试验代码，返回它打印的内容。能用参数、`scad`、`ql`、`math`，还能用 `model`（截到当前阶段已建好的实体，还没有时为 `None`），方便试选边、试圆角；不影响模型 | 过同一套静态检查（另外放行 `print`）；输出最多 2000 字符；每阶段最多 10 次；不计入失败次数 |
| `read_reference(name, section)` | 读 SCA 官方 skill 里的一篇文档。不给 `section` 时返回各节标题和开头 3000 字符；给了就返回那一节，最多 6000 字符 | `name` 只能取白名单里的名字 |

`read_reference` 的白名单共 10 篇：`discipline/` 下的 `feature-ordering`、`failure-and-repair`、`mechanical-modeling`、`datums-and-coordinate-systems`、`geometric-validation`、`manufacturing-boundaries`，`domains/` 下的 `part-modeling`、`sketch-and-features`、`standard-parts`，以及 `ql-playbook`。讲 notebook 文件结构、验证脚本写法、装配、导出的几篇不放进来：那些事在卡尺里由程序负责，给模型看反而会让它去做不该做的事。系统提示词里放一张我们自己写的中文目录，每篇一句话说明什么时候该读。文档原文是英文，不翻译。

所有工具说明的原文放进第二版的提示词文档，照旧逐字测试。

### 3.5 上下文与提示词

- 沿用 1.1 版的布局：每轮开头一张快照，轮内只追加，一轮结束后折叠。
- 快照多出：计划和每个阶段的状态、当前阶段、位置关系。
- 一个阶段通过后，这个阶段里的工具往来在下一次调用前折叠成一行（"S2 立板：通过，检查 7/7"）。这样阶段再多，轮内历史也不会一直变长；折叠只发生在阶段边界，前缀缓存在阶段内仍然有效。
- 系统提示词重写为第二版：流程和关卡、"先写检查再建模"的要求、怎么分阶段（借鉴官方 skill 的"先基体、后增减材、最后圆角倒角；先做一个再阵列"）、什么时候用 `probe` 和 `read_reference`。速查表保留并补上草图、标准件、抽壳三类的最小用法，每条写法先实测再写进去。

### 3.6 终检

最后一个阶段通过后，程序依次做三件事，全过才交付：

**(1) 全部检查再跑一遍。** 所有 `from_here` 检查对最终模型都要成立；每个 `source=user` 的参数至少被一条检查引用（沿用第一版的覆盖规则）。

**(2) 参数扰动验证。** 对每个 `source=user` 的参数（最多 12 个，超过时按需求单里的顺序取前 12 个并在结果里写明）：
- 把这个参数改掉：单位是 `1` 的整数加 1，其余乘 1.2。
- 用改后的参数重建模型；检查的期望值**冻结**在按原参数算出来的数字上。
- 至少一条检查不通过：这个参数被真正约束了，过关。
- 检查仍然全过：说明模型没用上这个参数，或者没有检查管它。不过关，把参数名退回给模型。
- 改后建不出来：换成乘 0.8（整数减 1）再试一次；还是建不出来就记为"无法扰动"，不算不过关，写进检查报告。

各参数的扰动并行运行，最多 4 个进程。这一步不调用大模型。

它能拦住的：参数改了但几何没变（1.1 版 `enclosure` 的失败）；检查和参数无关。它拦不住的：模型和检查"自洽地错"（比如都按叠放来算）。后者靠 3.2 的位置关系、下面的看图审查和用户自己看 3D。

**(3) 看图审查。** 只在审查用的模型能识图时做（见 4.3），否则跳过，交付卡片上写"未做看图审查"。
- 程序渲染四张图：等轴测、正视、俯视、右视（`render_screenshot_rpath` 的 `view` 参数，已实测支持角度元组和四视图）。
- 发起一次**独立**的模型调用：全新的上下文，只给审查者的提示词、需求单（零件、组成部分、位置关系、关键参数）和四张图。建模过程中的任何内容都不给它。
- 审查者必须用工具 `submit_review` 回答：对每个组成部分和每条位置关系给出"符合 / 不符合 / 看不出"和理由。
- 有"不符合"：退回建模模型，带上理由，计一次失败。一次交付最多审查 2 轮。
- 2 轮后仍有"不符合"：照常交付，但交付卡片上标出"看图审查有异议"并列出异议，由用户裁决。

### 3.7 案例库

**案例** 是一个目录，里面有一个 `case.yaml`：标题、标签、一句话需求、需求单、计划、全部特征代码、全部检查。

- **自带案例：** 8 个，放在包里的 `cad_agent/cases/`。它们是和评测任务**不同**的零件，覆盖不同的做法：拉伸加孔阵列、旋转体、抽壳、加强筋、草图轮廓拉伸、标准件齿轮、扫掠、圆角倒角的顺序。每个案例都要有测试：用真实 SCA 建出来、检查全过、扰动验证通过。
- **用户案例：** 放在数据目录的 `cases/`。交付之后界面上有"存为案例"，填标题和标签即可，不调用模型。
- **检索：** 进入规划时，程序用需求单（零件名、用途、组成部分）和每个案例（标题、标签、组成部分）算相似度：汉字二元组的重合加标签命中。不引入分词库和向量库。取分数过线的前 2 个。
- **给模型：** 作为一条"【参考案例】"消息放在规划那一轮的开头，每个案例给计划和特征代码，最多 3000 字符。提示词里写明"只供参考，尺寸和结构以需求单为准"。
- **日志：** 记下用了哪些案例。评测脚本加 `--cases on|off`，用来做"有案例库 / 无案例库"的对照。

自带案例不取自评测任务，是为了不让评测变成"抄答案"。

### 3.8 参数直改

交付之后，用户在参数面板里改数值并点"应用"：
1. 程序校验数值，更新需求单（改过的参数来源记为"用户"）。
2. 从 S1 起重新验证全部阶段，再跑终检的第 (1) 项。不做扰动验证和看图审查。全程不调用大模型。
3. 全过：存成新版本，变化说明写"手动修改参数：a 30 → 36"。
4. 没过：不存版本，参数退回原值，面板上显示哪条检查没过，并给一个"让助手处理"按钮（把这次改动作为一条用户消息发给模型）。

只在智能体空闲时可用。下一轮对话的快照由程序从当前状态生成，所以模型自然会看到新数值。

### 3.9 给装配留的口

只留一个口，不改目录结构：所有读写零件状态（需求单、计划、特征、检查、版本）的地方，都通过同一个函数 `Session.part_dir(part_id)` 取目录。这一版只有一个零件，id 固定为 `main`，这个函数返回会话目录本身，所以现有会话和现有测试的路径都不变。下一版做装配时，只需要让它返回各零件自己的子目录。除此之外不为装配写任何代码。

### 3.10 开关

新关卡各有一个配置开关，默认全开，写在 `[agent]` 里：`staged`（分阶段；关掉就退回 1.2 版的单阶段流程）、`mutation_check`（参数扰动验证）、`visual_review`（看图审查）、`cases`（案例库）。用途有两个：真模型评测时可以逐个关掉做对照；哪个关卡在某个模型上帮倒忙时，用户可以自己关。

实现上，分阶段流程全部写在新模块里，1.2 版的流程原样保留：`staged` 关掉时，工具说明、系统提示词、build 的返回都和 1.2 版逐字相同。这也让现有测试基本不用改。

## 4. 模型接口

### 4.1 接口改动

`LLM.chat` 多一个可选参数 `on_delta`：有文字片段到达时回调。两个实现都要支持逐字输出；思考内容不显示，只给界面一个"正在思考"的状态。`ScriptedLLM` 同步支持，测试里可以断言片段。

消息内容支持图片（看图审查用）：内部统一用 OpenAI 的 `image_url` 写法，适配层负责转换。

停止：`chat` 再多一个可选参数 `should_stop`，在收到每个片段时检查，为真就中断请求并抛出专门的异常，主循环据此结束本轮。

### 4.2 Claude 适配层

新文件 `cad_agent/llm/anthropic_client.py`，用官方 `anthropic` SDK，对内呈现同一个 `LLM` 接口：
- 消息和工具定义在两种格式之间转换（系统提示词单独传、工具调用和工具结果是内容块）。
- 用量换算成内部的六项（输入、输出、命中缓存、思考等）。
- 给系统提示词和每轮快照加缓存标记。
- 重试、报错信息和现有客户端的约定一致，信息里不含 key。

写这一节的实施计划时，接口细节以 Anthropic 官方文档为准，不凭记忆写。没有用户提供的 Anthropic key 之前，这一层只有假服务端的单元测试，文档里标明"未用真实接口验证"。

### 4.3 服务预设与能力

包内数据文件 `cad_agent/providers.toml`，每个预设有：显示名、接口类型（`openai` 或 `anthropic`）、默认地址、建议的模型名、key 的环境变量名、是否能识图（`yes` / `no` / `unknown`）。

预设：DeepSeek、智谱 GLM、Kimi、通义千问、OpenAI、Claude、自定义地址。各家的地址和模型名在实施时对照官方文档核实后再写入；拿不准的模型名留空让用户填。代码和预设里不写任何价格，价格仍由用户在设置里照价目页填，不填就只显示 token 数。

识图能力为 `unknown` 的（包括 DeepSeek，没有实测过）默认按不能识图处理。设置页有"测试识图"按钮：发一张很小的测试图，成功就把这个服务标成能识图。这一步由用户自己点，花的是用户自己的几厘钱。

阶段设置沿用 1.1 版的 `clarify`、`modeling`，新增 `review`（看图审查用哪个模型），不设时用基础模型。

### 4.4 key 的存取

取 key 的顺序：环境变量（预设里的变量名）→ 系统钥匙串（`keyring`，服务名 `caliper`，用户名为预设 id）。

规则在第一版的基础上不放松：key 不写进任何文件、配置、日志、测试、提交；界面上只显示后四位；程序里不打印。新增的只有一条路径：界面输入 → 本机接口 → 钥匙串 → 内存里的客户端。

## 5. 桌面端

### 5.1 结构

```
caliper（一个进程）
 ├─ 本机 HTTP 服务（127.0.0.1，随机端口）── 现有 web/ 的升级版
 │    ├─ 静态页面
 │    ├─ /api/…        操作
 │    └─ /api/events   推送（SSE）
 ├─ pywebview 窗口 ── 加载上面的页面
 └─ 智能体线程 ── 一个会话一个
```

- 窗口打不开时（缺 WebView2 等），`caliper --browser` 退回到用默认浏览器打开同一个页面。
- 轮询改推送：服务端把事件（文字片段、工具开始和结束、阶段状态、检查结果、新版本）通过 SSE 推给页面。页面断线自动重连，重连后先取一次完整状态。
- **本机接口的保护：** 每次启动生成一个随机令牌，所有 `/api/` 请求必须带上；同时检查 `Origin`。这样别的网页和本机其他程序不能调用这些接口（其中包括写 key 的接口）。
- 停止：页面调用 `/api/stop`，置一个标志；主循环在每次模型调用、每个片段、每次工具调用之间检查；正在跑的沙盒子进程被结束。本轮以"已停止"结束，已经写下的特征和检查保留。

### 5.2 画面

| 画面 | 内容 |
|---|---|
| 首次引导 | 三步：选模型服务 → 粘贴 key 并"测试连接" → 完成。任何一步都可以选"先看示例"跳过 |
| 主界面 | 三栏，见下 |
| 设置 | 模型服务和模型名、key（只显示后四位，可替换和删除）、价格、测试识图、各阶段模型、外观（浅色 / 深色 / 跟随系统）、数据目录位置、版本和更新方法 |
| 案例库 | 自带案例和用户案例的列表，可查看、删除用户案例 |
| 示例会话 | 只读回放，不需要 key |

**主界面三栏：**
- **左：会话。** 历史会话列表（零件名、时间、版本数），新建、重命名、删除。点开旧会话可以接着做：状态文件原样读回，对话上下文从日志恢复成折叠后的各轮。
- **中：对话。** 逐字输出；工具调用显示成一棵可折叠的树（阶段是树干，工具是分支）；提问时列出问题和逐条回答；确认时显示需求单卡片（参数来源分"用户"和"建议"，带位置关系）；交付时显示版本卡片（检查通过数、扰动验证结果、看图审查结论、下载）。输入框旁边在运行时变成"停止"。
- **右：工作台。** 四个页签：
  - 模型：3D 视图，带轮廓线、外形尺寸标注、线框切换、重置视角；底部一条阶段刻度，拖动可以看零件一个阶段一个阶段长出来。
  - 检查：逐条列出期望值、实测值、是否通过；扰动验证和看图审查各有一块。
  - 参数：需求单的参数表，每个数值可以直接改或拖滑块（范围为当前值的 0.5 到 1.5 倍），点"应用"生效（见 3.8）。
  - 版本：各版本缩略图，任选两版对比参数变化和截图。导出 STEP、STL、参数化源文件，或在文件夹中显示。

**示例会话：** 本轮只带一个，就是现有的 `demo/phone_stand`（1.1 版的真实录制，界面上标明"录制于 1.1 版"，它没有阶段信息，按单阶段显示）。新流程的示例要等有了真实运行之后再录，不做假的。

### 5.3 视觉规范：图纸与蓝图

**原则：** 界面就是一张工程图。唯一的装饰是制图语言本身——尺寸线、标题栏、等宽数字。不用阴影、渐变、圆角卡片。

| 项 | 浅色（图纸） | 深色（蓝图） |
|---|---|---|
| 底色 | `#F4F1EA` 米白纸 | `#0F2A4A` 深蓝 |
| 主线和正文 | `#1B1B1B` 墨黑 | `#E6EEF8` 白线 |
| 次要文字 | `#6B675E` | `#9DB7D6` |
| 强调（尺寸线、链接、当前项） | `#1F4FD8` 制图蓝 | `#FFD166` 琥珀 |
| 通过 / 不通过 | `#2E6B3F` / `#B3261E` | `#8FD6A3` / `#FF8A80` |
| 3D 零件 | 浅灰实体、墨色轮廓线 | 半透明浅蓝实体、白色轮廓线 |

- **线：** 分隔全部用 1px 实线，圆角 0 到 2px。
- **字：** 界面文字用系统字体（Windows 微软雅黑 UI，Mac 苹方）；数字、参数名、工具调用、代码用等宽字体（Cascadia Mono / SF Mono / Consolas）。不加载任何网络字体，页面离线可用。
- **尺寸线：** 用作小节标题的装饰线、阶段进度（一条带刻度的尺寸线，S1 到 Sn 是刻度，当前阶段用强调色）、3D 视图里的外形尺寸标注。
- **标题栏：** 工作台右下角一块像图纸标题栏的表格：零件名、版本、当前阶段、模型名、本次会话费用、缓存命中率、日期。它取代普通的状态栏，是这个界面最有辨识度的地方。
- **动效：** 只有逐字输出和阶段刻度的推进；遵守系统的"减少动态效果"设置。
- 两套配色都要检查文字对比度不低于 4.5:1。

实施界面那份计划时，先按项目里的界面一致性流程梳理现有页面的写法，再动手。

## 6. 安装与分发

### 6.1 安装命令

```
Windows（PowerShell）:
  irm https://raw.githubusercontent.com/DingZhen-zhr/computer-graphics-project/master/install.ps1 | iex

Mac（终端）:
  curl -fsSL https://raw.githubusercontent.com/DingZhen-zhr/computer-graphics-project/master/install.sh | sh
```

脚本做的事：
1. 检查平台（Windows x64；Mac 必须是 Apple 芯片且 macOS 14 以上），不符合就说明原因并退出。
2. 没有 uv 就安装 uv（它的官方安装脚本）。
3. `uv tool install`，指定 Python 3.12，从本仓库的发布标签安装。用户电脑上不需要预先有 Python。
4. 建快捷方式：Windows 是开始菜单和桌面；Mac 是 `~/Applications/Caliper.app`（脚本在本机生成的一个启动器）。
5. 运行 `caliper doctor`，把结果打印出来。

脚本支持国内镜像：加参数后，PyPI 和 Python 下载走镜像。GitHub 访问不了时，README 里给出"下载压缩包后本地安装"的办法。

发布方式：打 git 标签（这一版是 `v2.0.0`）；安装脚本里写明要装的标签，发布时一起更新。Python 包的发行名改为 `caliper-cad`，包目录名仍是 `cad_agent`（不改导入，免得动全部测试）。

## 10. 风险

| 风险 | 应对 |
|---|---|
