# CAD 建模智能体 · 第 1.1 版设计（省钱、提速、更稳）

日期：2026-11-09　状态：待审阅
基于：第一版设计 `2026-11-09-cad-agent-design.md`、联调结果 `docs/results-v1.md`、三个任务的 `log.jsonl` 逐次拆解。

## 1. 目标与成功标准

**目标：** 能力不降，花费大幅下降，结果更稳；仍然是"换模型只改配置"。核心思路不变：程序管流程，模型只做判断。这一版把更多"确定的步骤"从模型手里收回到程序里，并且让每次调用模型时重复发送的内容尽量走缓存。

**这一版不做：** 经验复用（仍是第二版）、图片输入、装配；不改沙盒、检查器的计算方法；不用"限制输出长度（max_tokens）"来省钱（会把模型的思考截断，调用作废反而更贵）。

**成功标准：**
1. 3 个开发任务（手机支架、法兰盘、L 形支架）各跑 3 遍：成功至少 8/9，且每个任务至少 2/3。
2. 费用不超过基线的 1/3。比法：每个开发任务取 3 遍费用的平均值，3 个任务的平均值相加，和基线 3 个任务的费用之和比。基线 = 第一版流程加上新的计量（第 4 节）后跑一遍的结果；费用按配置里的价目表算。
3. 2 个留出任务（第 8.2 节）各跑 1 遍，结果如实报告。不设通过门槛，也不许为它们调提示词。
4. 换模型仍然只改配置；全部测试通过。
5. 耗时、调用次数、输入（命中缓存 / 没命中）、输出（其中思考）都要报告，但不设门槛。

最多 3 轮提示词迭代后仍达不到 1、2 条时，如实写进结果文档，不放宽标准。

## 2. 第一版的问题（日志实测）

三个任务共 53 次模型调用，输入 1,046,686 token，输出 115,073 token。

| # | 问题 | 证据 |
|---|---|---|
| P1 | 三成调用只是在"按按钮" | 15 次调用只输出二十来个 token（只为调用 `build` 或 `request_confirmation`），每次却要重发整段对话，合计输入 343,289，占全部输入的 33% |
| P2 | 缓存基本用不上 | 状态消息每次调用都重新生成，并且排在对话历史**前面**；里面"工具调用还可 N 次"每次都变，所以它后面的整段历史每次都和上一次不同，前缀缓存最多只能命中最前面的系统提示词 |
| P3 | 历史只增不减 | 每一轮的工具调用细节（整段需求单补丁、检查项 JSON、特征代码）一直留着，而它们的当前版本本来就在状态消息里。L 形支架建模那一轮，每次调用的输入从 2.0 万涨到 4.1 万；修改那一轮仍要 2.6 万 |
| P4 | 输出的大头是思考，而且同一轮里会被反复计入输入 | 9 次调用的输出占全部输出的 81%。最长一次是手机支架整理需求单：输出 21,279 token，用时 142 秒（整个任务 275 秒）。同一轮内，上一次的思考会出现在下一次的输入里：手机支架建模第一次调用输出 11,651，下一次输入就从 12,352 涨到 24,070 |
| P5 | 算不出真钱 | 客户端只记了 prompt / completion / total 三个数，没记命中缓存多少、思考多少 |
| P6 | 缺检查也算一次建模失败 | 法兰盘、L 形支架第一次 build 都只是"有用户参数没被检查覆盖"，几何本身没问题，却各用掉一次修复机会 |

## 4. A：计量

**用量字段。** `LLMReply.usage` 统一成 5 个整数字段，取不到的记 0：

| 字段 | 取法（按顺序，取到第一个为止） |
|---|---|
| `prompt_tokens`、`completion_tokens`、`total_tokens` | 和第一版相同 |
| `cached_tokens` | `usage.prompt_cache_hit_tokens`（DeepSeek）→ `usage.prompt_tokens_details.cached_tokens`（OpenAI 风格）→ 0 |
| `reasoning_tokens` | `usage.completion_tokens_details.reasoning_tokens` → 0 |

DeepSeek 实际返回哪些字段，由第一个任务用真实接口探测确认，写进 `docs/llm-api-notes.md`。

**价目表。** 配置里可选的 `[llm.pricing]`：`input_hit`、`input_miss`、`output`，单位是"元 / 百万 token"，由用户照模型服务的价目页填写，代码里不写任何价格。

每次调用的费用 = (cached × input_hit + (prompt − cached) × input_miss + completion × output) / 1,000,000。没配价目表时，费用记为空，报告里显示"-"。

**记录。**
- 日志里每条 `assistant` 记录完整的 5 个用量字段和本次费用。
- 每轮结束的记录（`reply`、`question`、`confirm`、`delivered`、`failed`）再加上本轮的命中缓存合计、思考合计、费用合计。
- 命令行每轮结束显示一行："本轮模型调用 N 次，输入 X（命中 Y）、输出 Z（思考 W），约 ¥C"。

**评测。**
- `benchmarks.run` 增加 `--repeat N`（默认 1）和 `--set dev|holdout|all`（默认 dev）。
- 结果按任务汇总：成功次数 / N，以及平均费用、平均耗时、平均调用次数、平均输入（命中 / 没命中）、平均输出（其中思考）。
- `results.json` 保留每一遍的原始数据。
- 新增 `python -m benchmarks.compare 旧/results.json 新/results.json`：输出按任务的前后对比表（Markdown）。

**基线。** A 做完、B~E 还没动时，用第一版流程跑一遍 3 个开发任务（各 1 遍），作为基线。第一版留下的 `results.json` 没有命中缓存的数字，不能直接当基线用。

## 5. B：上下文布局

**每次调用发给模型的消息，从前到后：**

1. `system`：系统提示词 + 速查表（和第一版一样，整个会话不变）。
2. 之前各轮的**折叠版**：每轮一条 `user`（用户原话；确认那一轮用"（用户已确认需求单）"）和一条 `assistant`（见下表）。
3. 本轮的 `user` 消息：**快照**在前、用户原话在后，格式见提示词文档。
4. 本轮已经发生的 `assistant` / `tool` 消息，只往后追加。

**规则：**
- 快照在一轮开始时生成一次，这一轮中间不再改。同一轮里，第 k+1 次调用发出的消息，开头必须和第 k 次发出的消息完全相同（有测试保证），这样上一次发过的内容都能命中缓存。
- 一轮结束后，这一轮的工具调用细节折叠掉。当前的真实状态都在下一轮的新快照里。
- 工具列表和第一版一样，按当前能用的工具给出；只有需求单的确认状态变了才会变，平时不影响缓存。

折叠后的 `assistant` 内容按本轮结局决定：

| 本轮结局 | 折叠后保留 |
|---|---|
| question | 给用户看的文字原样保留（用户会按编号回答） |
| confirm | "（已把需求单发给用户确认）" |
| delivered | 交付文字的第一行和"本版变化"那一行 |
| failed、reply | 给用户看的文字原样保留 |

**快照内容：**
- 澄清阶段：阶段、需求单 JSON。
- 建模阶段：阶段、需求单 JSON、按顺序列出的每个特征（slug、role、完整代码）、检查项 JSON、上次 build 返回给模型的原样 JSON（没运行过就写"未运行"）。

特征代码和检查项要进快照，是因为旧轮折叠后，模型只能从快照里看到自己以前写过什么。

**剩余次数：**
- 不再放在每次调用的状态里。build 的返回本来就带 `failures_left`。
- 本轮工具调用只剩 5 次或更少时，程序在每个工具返回的 JSON 里加一个字段 `"warning": "本轮工具调用只剩 N 次"`。

快照放在 `user` 消息里，不用额外的 `system` 消息，因为所有 OpenAI 兼容接口都接受这种写法。快照用醒目的标题标明"程序生成，不是用户说的话"。

## 6. C：程序代按按钮

**C1 自动请确认。** 需求单当前未确认（包括建模阶段里因为改了建议值而被取消确认的情况），一次回复里的工具全部执行完、本轮还没结束时，如果同时满足下面这些条件，程序自己调用 `request_confirmation` 并结束本轮：
- 这次回复里至少有一次 `update_brief` 成功；
- 这次回复里没有 `ask_user`，也没有 `request_confirmation`；
- 需求单里有参数，并且没有待问问题。

`request_confirmation` 工具保留，模型也可以自己调用。

**C2 改参数自动重建。** 需求单在这次回复前后都是已确认的，并且同时满足下面这些条件时，程序替模型调用一次 `build`：
- 一次回复里只有 `update_brief`，而且全部成功；
- 回复前后参数名集合不变、组成部分不变、没有待问问题；
- 已经有特征和检查项。

具体做法是在历史里追加一条 `assistant` 消息（`content` 为空，`tool_calls` 里只有一个 `build`，id 为 `auto-build-<序号>`）和对应的 `tool` 消息，之后和模型自己调用 `build` 完全一样处理：通过就交付，没通过就继续让模型修。

如果第一个任务的接口探测发现服务端不接受这种程序补的调用，改为追加一条 `user` 消息："【程序自动运行了 build，结果如下】" 加上返回的 JSON，并在偏离记录里写明。

**C3 一次回复做完。**
- 提示词和工具说明都要求：写完全部特征和检查项后，在**同一次回复里最后**调用 `build`；澄清时，`update_brief` 和 `ask_user` 也放在同一次回复里。
- 程序规则：同一次回复里，只要前面有一个工具调用出错（返回 JSON 的顶层有 `error`），后面的 `build` 就不运行，返回 `{"error": "同一次回复里前面的调用出错了，这次 build 没有运行，也不算失败。先改好出错的调用，再调用 build。"}`，不计失败次数。

**C4 缺检查不算失败。** build 时几何没出错、检查全部通过、只是有用户参数没被覆盖：不交付、不计失败次数，返回内容和第一版一样。`set_checks` 本来就会当场返回 `missing_coverage`。如果模型一直补不上，靠每轮 40 次工具调用的上限兜底。

## 7. D：按阶段选模型、透传参数

**配置：**

```toml
[llm]
base_url = "https://api.deepseek.com"
model = "deepseek-flash"
api_key_env = "DEEPSEEK_API_KEY"
temperature = 0.2
extra_body = {}            # 可选：原样作为请求的 extra_body 发出去

[llm.pricing]              # 可选：元 / 百万 token，照价目页填
input_hit = 0
input_miss = 0
output = 0

[llm.clarify]              # 可选：澄清阶段（需求单未确认）覆盖 model、temperature、extra_body、pricing
[llm.modeling]             # 可选：建模阶段覆盖同样几项
```

**规则：**
- 阶段在一轮开始、处理完确认之后决定：需求单已确认就是建模阶段，否则是澄清阶段。这一轮内不换模型，保证缓存连续。
- 没写覆盖段的阶段用 `[llm]`。默认两个阶段都用同一个模型，和现在的行为一样。
- 模拟用户只用 `[llm]`。
- 代码里不写任何厂商专用的参数名。关思考、调思考强度之类，全部通过 `extra_body` 透传。

**实验。** 账号里可用的模型是 `deepseek-flash` 和 `deepseek-v4-pro`。能不能通过 `extra_body` 关掉或降低 `deepseek-flash` 的思考，由第一个任务探测，结果写进 `docs/llm-api-notes.md`。

最终评测跑两组配置：
- **E1**：两个阶段都用默认的 `deepseek-flash`。
- **E2**：澄清阶段关掉或降低思考（探测发现可行的参数时才跑）。

在满足成功标准的前提下，选更便宜的一组写进 `config.example.toml`。探测下来没有可行参数的话，D 的代码照样交付，结果文档写明"没法测"。

## 8. E：做得更好

### 8.1 检查写法速查

速查表新增一节"检查写法"，覆盖这些常见参数：
- 总体尺寸
- 板厚
- 孔径
- 孔数
- 孔位
- 槽或缺口宽度
- 圆角半径
- 倒角尺寸
- 两面夹角

每条给出一段检查 JSON 示例和一句说明。每条都要有测试：用 SCA 建一个小模型，参数正确时检查通过，参数偏 20% 时检查不通过。用现有检查类型测不了的参数，写明"用什么间接测"。如果连间接测也做不到，就不写这一条，并在笔记里说明原因。

### 8.2 留出任务

两个新任务只用来测，不许为它们调提示词；提示词迭代只能看开发任务的日志。

**enclosure（电路板小盒）**
- 开头一句："做一个装电路板的小盒子"。
- 隐藏需求：
  - 外形 80×50×30 mm（长×宽×高），上面敞口，这次不做盖子；
  - 四面侧壁厚 2 mm，底厚 2 mm；
  - 正面（朝 -y 的那面墙）正中开一个 USB 口：宽 12 mm、高 6 mm，下沿离盒底 8 mm；
  - 不要圆角，不要安装孔，盒子里面没有别的结构。
- 修改请求："四面侧壁的壁厚改成 3 mm，底厚不变"。
- 验收（初始）：
  - bbox x/y/z = 80/50/30（tol 0.5）；
  - 体积 21968（rel_tol 0.02；120000 − 76·46·28 − 12·6·2）；
  - 点在材料里：[0,0,1.5]、[38.5,0,15]、[20,-24,15]、[0,-24,7]、[0,-24,15]、[7,-24,11]；
  - 点不在材料里：[0,0,2.5]、[0,0,15]、[37.5,0,15]、[20,-22.5,15]、[0,-24,11]、[5,-24,11]。
- 验收（修改后）：
  - bbox 不变；
  - 体积 28616（rel_tol 0.02；120000 − 74·44·28 − 12·6·3）；
  - 点在材料里：[0,0,1.5]、[37.5,0,15]、[20,-22.5,15]、[0,-23.5,7]、[7,-23.5,11]；
  - 点不在材料里：[0,0,2.5]、[36.5,0,15]、[20,-21.5,15]、[0,-23.5,11]、[5,-23.5,11]。

**stepped_shaft（阶梯轴）**
- 开头一句："做一根阶梯轴"。
- 隐藏需求：
  - 竖直放，轴线沿 z，从下往上三段：直径 20 长 30、直径 30 长 20、直径 16 长 40，总长 90；
  - 第二段正中（离底面 40 mm）有一个直径 6 的横向通孔，沿 y 方向穿透；
  - 不要倒角、圆角、键槽。
- 修改请求："最上面那段直径改成 18"。
- 验收（初始）：
  - bbox x/y/z = 30/30/90（tol 0.5）；
  - 点在材料里：[9.5,0,15]、[14.5,0,35]、[7.5,0,70]、[12,0,40]、[0,0,43.5]；
  - 点不在材料里：[10.5,0,15]、[15.5,0,35]、[8.5,0,70]、[0,0,40]、[0,14,40]、[0,0,42.5]。
- 验收（修改后）：
  - bbox 不变；
  - 第三段改为：点在材料里 [8.5,0,70]、点不在材料里 [9.5,0,70]；
  - 其余各点和初始相同。

两个任务都要像第一版那样，用 SCA 写"标准答案"模型做正反两面的测试：标准答案能通过验收；没改参数的旧模型过不了修改后的验收。

### 8.3 提示词修订

全文写在第 1.1 版的提示词文档里，执行时逐字照抄。要点：
- 说明快照是什么、以快照为准、旧轮细节不保留。
- 澄清时 `update_brief` 和 `ask_user` 放在同一次回复里；澄清时只判断尺寸之间有没有矛盾，不要设计具体的建模步骤。
- 需求单整理完会由程序自动请用户确认。
- 建模时同一次回复写完特征、检查，最后调用 `build`。
- 交付后只改参数值的，只调用 `update_brief`，程序会自动重建。

## 9. 评测流程与花费

1. A 做完后跑基线（3 个开发任务各 1 遍）。
2. B~E 做完后，用 E1 跑开发任务各 3 遍、留出任务各 1 遍；探测有可行参数时，再用 E2 跑开发任务各 3 遍。
3. 达不到标准时，最多 3 轮提示词迭代，每轮只看开发任务的日志，然后重跑开发任务各 3 遍。
4. 写 `docs/results-v1.1.md`，内容包括：
   - 基线和新版的对比表；
   - 逐条对照成功标准；
   - E1/E2 的结论；
   - 留出任务的结果；
   - 没做到的地方。

跑基线前，用户要先在 `config.toml` 里填好 `[llm.pricing]`（价格不是机密，但必须由用户照价目页填）。

**粗估花费：** 基线大约等于第一版那次评测；E1 共 11 个"任务遍"，如果达到 1/3 的目标，约等于 3.7 个第一版任务；E2 再加约 3 个。总计大约是第一版那次评测的 2~3 倍。

| `benchmarks/run.py`、`benchmarks/compare.py`、`benchmarks/tasks/` | `--repeat`、`--set`、费用列、前后对比、两个留出任务 |

第一版里断言了"被这一版有意改掉的行为"的测试（例如状态消息格式、缺检查计失败），只按计划里列出的清单修改，并逐条写明原因；清单以外的第一版测试一律不动。

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| 折叠历史后模型忘了之前的推理，追问变多或修复变差 | 快照里放完整的特征代码、检查项和上次 build 结果；评测和基线对比，成功率下降就在结果里写明，并回到提示词迭代 |
| 服务端不接受程序补的 `build` 调用 | 第一个任务先探测；不接受就换成 `user` 消息的写法（第 6 节 C2） |
| 自动请确认来得太早，模型本想再问 | 用户在确认时可以指出不对，流程和第一版一样回到澄清；模拟用户的规则 4 本来就会逐条核对 |
| 一次回复写太多，JSON 出错 | 每个工具调用单独校验、单独返回错误；同一次回复里前面出错时 `build` 跳过且不计失败 |
| 缓存、思考计入输入的机制是服务端的事，可能和预想不同 | 用实测的 `cached_tokens`、`reasoning_tokens` 说话，结论只写测到的 |
| 只对 3 个开发任务有效 | 留出任务只测不调，结果单独报告 |
